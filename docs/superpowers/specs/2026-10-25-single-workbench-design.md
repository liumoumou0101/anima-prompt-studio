# 单一工作台改造方案

日期：2026-10-25。状态：可评审方案，尚未实施。

用户已选方向：保留现有业务与数据能力，重新设计唯一工作台；本轮交付具体方案、结构草图和分阶段清单。下文中的字段、接口、数值和布局均为本轮建议，不能当作已实现能力或用户逐项确认过的选择。

配套：[分阶段修改清单](../plans/2026-10-25-single-workbench.md)。审查证据位于 `reports/ui-audit-20261025/ui-functional-audit.html`；该目录被 Git 忽略。交互草图在本次聊天内展示；其示例不连接 LLM、云主机或生图服务。

## 1. 改造结果与边界

用户日常只需完成：打开创作 → 编辑或 AI 改写 → 调整少量参数 → 生成 → 从满意版本继续。服务器地址不再和工作流混在一个选择器里；多份废弃连接不会迫使用户逐项试错。

| 方向 | 收益与代价 | 决策 |
| --- | --- | --- |
| 在两套布局上局部修补 | 改动较少，但操作与状态仍重复，后续维护继续分叉 | 不作为最终形态；仅先修已确认故障 |
| 重写前后端与存储 | 可重新划分所有模块，但会重新承担历史、恢复、任务幂等与资源管理风险 | 不采用 |
| 保留业务与存储，替换交互控制和唯一工作台 | 能保留现有能力，同时解决版本、参数与环境的耦合 | 本次选定方向 |

统一的是工作台组件、交互规则和视觉体系。保留明亮 / 深色 / 跟随系统主题；移除 studio / editorial 布局选择。英文原文编辑仍然存在，成为同一工作台中的使用路径。画廊、标签、画师、参考库、设置和工作流管理仍有各自页面。

必须保留：正负提示词、中文修改、改写模式、要求与锁定、角色画师与场景工具、标签与个人词条、参考导入、版本与分支、图片对照与复用、LoRA、原文直出、精确 Seed、任务恢复及实际输入快照。旧 `WorkbenchPage.tsx` 不在当前主路由，但其中独有能力必须逐项处置，不能因名称是“旧版”直接删除。

首版不包含：任意 ComfyUI 节点图自动转表单、自动购买/创建云实例、自动信任未知 SSH 主机、根据价格自动迁移、已受理任务跨环境重发、用视觉相似度自动认定改写失败。

## 2. 证据与待查项

| 事项 | 本轮审查事实 | 对方案的约束 |
| --- | --- | --- |
| 连续 AI 改写只能撤一次 | 用户确认是界面撤销按钮；受控测试中三次改写、三次撤销、三次重做通过 | 现场原因尚未复现；先补现场状态证据，不能宣称修复了“一步上限” |
| 快捷撤销丢失 | 当前栈仅在组件内存中，部分 adopt、切页及刷新会清除 | 操作日志需要独立生命周期与持久化 |
| 换执行目标覆盖参数 | 工作台会显式应用默认配方，复现 22 steps / 3.2 CFG 变为 35 / 4.5 | 环境选择与配方应用必须解耦 |
| 原文转工作台断链 | producer 写入 direct import，当前实际路由没有消费该入口 | 先补真实路由链测试和导入回执 |
| 旧连接难选 | 目标是环境×工作流组合；ready 缓存或 SSH 已确认不等于实时可执行 | 后端在当前创作条件下筛选并探测环境 |
| 低屏高与嵌套折叠 | 固定底部区和多层工具遮挡内容 | 移除大块固定 dock，主编辑区优先 |

此前前端 524 项与选定后端 145 项通过，仅代表审查时的回归基线；未验证真实 LLM 改写质量、GPU 出图质量和云平台性能。本方案没有把这些结果升级为新功能已经通过。

### 尺寸与操作规则

- 宽度 ≥1024px：两列；导航约 56px，右侧 360–420px，左侧使用剩余宽度。1366×768 是主要验收尺寸。
- 宽度 <1024px：主内容使用“编辑 / 结果”单栏切换，参数和版本打开完整面板，关闭回到原位置；900×768 不再挤两列。390px 用于溢出和触控检查。
- 浏览器放大至 200% 时按可用 CSS 宽度自然折叠。主编辑区不因展开提示条被压成不足一段文字的高度。
- 底部操作条属于布局流，常态一行，窄屏可换行；不使用覆盖页面的 fixed dock。主面板最多各自一层滚动，弹窗按钮不受底栏遮挡。
- “更新提示词”只改写；“生成图片”使用当前可见文本。存在未应用意见时，生成区明确显示“意见尚未应用，本次使用当前提示词”，保留直接生成能力。
- “更新并生成”放在更新按钮的菜单中；只有改写成功、基点未变化、生成预检通过才执行。失败只保留成功完成的步骤，不隐式重试生图。
- 要求、锁定、角色画师和场景入口在编辑区同一层可见；详细内容可展开一次，不再三层套叠。
- 结果显示关联版本、当次实际参数、环境、工作流版本和图片缩略图；技术 ID 放详情与诊断，不占主列表。
- 标签和参考使用统一的目的地与范围预览。保留“添加到要求”“直接追加文本”“新建创作”之间的语义差别，展示实际写到哪里。

## 4. 版本与撤销

### 4.1 三种不同动作

| 入口 | 内容范围 | 参数与运行条件 | 后续历史 |
| --- | --- | --- | --- |
| 撤销 / 重做 | 撤回最近完整操作所改变的字段 | 只撤回该操作明确影响的参数 | 生图记录与图片不删除 |
| 提示词版本 → 用此版本继续编辑 | 正负词、改写模式及对应要求、内容标签和内容锁定 | 保留当前模型、工作流、参数、LoRA与执行策略；旧资源要求不能悄悄变成新绑定 | 新建当前节点，标明来源；保留之后所有版本 |
| 图片 → 从这张继续 | 图对应内容与当时创作条件 | 恢复已知模型、工作流版本、参数和资源要求；当前执行策略保持不变 | 保留原图与后续记录；不自动生图 |

旧图继续的默认行为沿用 [2026-09-21 约定](2026-09-21-workbench-history-and-undo-design.md)，并保留“只用提示词”次级动作。旧图中的环境 ID 是来源证据，不能强制复活失效云实例；再次运行仍按当前自动/固定策略寻找相同创作条件可用的环境。

内容与资源需显式分开：提示词版本恢复带回语义要求，不复制旧 LoRA 文件映射、旧模型绑定或环境指纹。如果旧文本需要当前未启用的 LoRA，显示资源差异并在生成前解决。缺少完整内容快照时，清除不匹配的中文记忆与内容锁定，以载入文本作为新改写依据，不借下一次 AI 请求自动补回较新的旧要求。

版本显示稳定的用户编号、中文修改摘要、时间、类型、关联缩略图和“当前起点”。支持按摘要/文本搜索、只看有图/全部记录；点击先预览，卡片直接提供“用此版本继续编辑”，无需进入更多菜单。“另开创作”是次级选项。底层 revision 与用户版本编号不是一回事，不能把并发保存次数直接当作用户动作。

### 4.2 操作日志

- 每次实际生效的 AI 改写独立一步；没有内容变化的响应不制造虚假撤销节点。
- 手动输入按具体字段合并，建议停顿阈值 800ms；失焦、字段切换、输入法一次提交和离散控件操作形成边界。不能按整个 settings 对象合并不同参数。
- 操作记录拟为 `EditOperation {id, kind, scope, before, after, label, createdAt, baseRevision, editorEpoch}`。只保存 scope 内字段的 before/after，撤销 AI 不复写后来保留的执行配置。
- `EditorJournal {schemaVersion: 1, workspaceId, documentId, cursor, entries, baseFingerprint, editorEpoch}` 与当前草稿在同一 IndexedDB 事务保存。快捷链最多 50 步；截断快捷链前，其完整快照必须已经在服务器 checkpoint 或本地待同步 outbox 中可恢复，不能直接丢弃。
- 文本草稿可以短防抖写入；AI、恢复、参数应用等完整动作立即持久化。显示“已保存”必须发生在写入成功后。突然断电不承诺恢复尚未落盘的最后输入。
- 切页、刷新、正常重启能恢复持久化链。服务器 revision 只要是本窗口自己的保存，不重置快捷链；远端冲突合并后建立新基点，旧链作为恢复快照可找回，不直接跨基点回放。
- 未发送意见独立保存。撤销 AI 时仅当输入框为空才找回该次意见；用户新输入不能被覆盖。
- 恢复旧版本前事务备份当前完整草稿；失败则原地不变。恢复操作本身一步可撤销；新编辑可以结束快捷重做链，但不能删除服务器历史。
- 旧 localStorage 草稿只迁移已有当前状态，不捏造过去的操作。各窗口使用既有文档身份隔离；窗口克隆不共享可写游标。存储损坏保留原始恢复材料。

服务器 checkpoint 的创建事件明确为：有效 AI 改写、完成合并的一段手工编辑、离散参数/模型操作、显式保存、历史继续以及生成前冻结。一次操作用稳定 operationId 去重；AI 或生成已有相同版本快照时引用它，不额外复制。checkpoint 是不可变历史记录，记录 baseRevision 和内容来源，不通过保存历史副本强行覆盖当前工作区。离线时放入与草稿同事务的 outbox，重连后按 operationId 幂等同步。用户 V 编号由服务端为稳定 checkpoint ID 分配并持久化；待同步显示“本地版本”，不按列表位置临时编号。默认版本列表突出内容与图片变化，参数操作可在“全部操作”查看。

超过 50 步时缩短快捷链，不缩短恢复记录。只有服务器已确认或独立本地恢复快照已成功写入才能淘汰内存里的唯一副本；如果存储失败，保留尚未备份的内存数据并提示保存故障，50 步是正常持久化条件下的快捷链上限。

### 4.3 异步与冲突

所有异步结果检查 workspaceId、requestId 与 editorEpoch。恢复、切换会话或改变改写基点时使旧请求失效，停止“更新并生成”的后半段。前端取消不足以证明后端没写入；后端原有 revision CAS 必须保留。

上下文 token 按 `(workspaceId, documentId)` 持久化隔离。切页/取消仅使该文档旧请求失效，不写草稿、不增加内容版本，也不取消另一窗口的请求。保存恢复后的新基点则在同一工作区事务中使本窗口旧 token 失效并按 revision CAS 保存；其他窗口仍由 revision CAS 防止过时写入。恢复携带稳定 operationId，同操作丢响应重试返回原恢复回执。

后端在 LLM 调用前及最终写入事务内都校验 token。若旧 turn 先完成，恢复收到 revision 冲突，先保存本地备份并进入现有冲突处理，不能强行覆盖。已接受的生图继续使用冻结输入，完成结果只挂回原节点。

## 5. 参数与工作流

### 5.1 三层状态

| 状态 | 保存内容 | 变化规则 |
| --- | --- | --- |
| 创作内容 | 正负词、要求、模式、内容锁定、来源 | AI / 文本编辑 / 版本恢复修改 |
| 创作配置 | 模型、工作流及版本、配方基线、字段覆盖、LoRA与资源要求 | 显式参数动作修改 |
| 执行策略 | 自动 / 固定、偏好顺序、允许的环境 | 环境设置修改，不修改前两层 |

工作流选择显示用途、收藏/最近使用、兼容模型和版本。默认复用上次选择的稳定工作流，不在生成时替用户改成另一模板。环境列表独立显示，工作流库与模板管理留在设置。

### 5.2 参数界面与来源

常用：画幅、宽高、张数、随机/固定种子。采样：Steps、CFG、Sampler、Scheduler。工作流特有参数与 LoRA 分组独立，不放在多层折叠底部。

保留 `baseRecipeId` 和逐字段 `overrides`；每个字段可标“已修改”，显示推荐值，并可单项恢复。单纯更换环境必须保持所有创作值不变。选择配方先展示改变项，显式“应用配方”作为一个可撤销动作；自动初始化只发生在新建空配置时。

更换模型/工作流时保留键、类型、范围兼容的手动值。不兼容项显示原因和建议值，用户显式应用后才替换；尚未解决时禁止生成，仍可编辑文本。自动环境模式按模板声明验证输入，再排除不能执行这些值的环境，不能取所有旧环境能力的交集来压缩可用参数。

数值编辑期间允许空字符串；失焦/提交校验后保留错误输入并就近提示，不把空值转换为 0。Seed 用十进制字符串保存与传输，随机使用显式模式；沿用后端允许范围，不转成会丢精度的 JS Number。模板固定字段显示固定值及原因。缺少能力信息显示“待检测”，不能假装支持。

### 5.3 工作流参数声明

拟新增 `WorkflowParameterSchema {version, workflowId, templateRevision, fields}`；字段包含 `key, label, type, default, min, max, step, enum, group, binding, readOnlyReason`。binding 只允许受校验的已声明节点输入，不提供任意路径求值。

首版基础字段：width、height、steps、cfg、sampler、scheduler、seed、batch_size。高清修复的明确绑定字段：refiner_steps、refiner_cfg、refiner_sampler、refiner_scheduler、refiner_denoise、upscale_factor。第二阶段 Seed 沿用当前派生规则并说明来源。实际可编辑性由模板决定；不能为缺少第二阶段的工作流凭空加控件。

复杂未声明图保留高级 JSON 和“模板固定”提示。任务接受时冻结 schema 版本、工作流版本、字段覆盖、解析结果与资源映射；历史不会随模板更新而漂移。

## 6. 自动执行环境

### 6.1 用户看到的行为

默认显示“执行环境：自动”，展开可看“预计可用 / 检测时间 / 未通过原因”，也可固定某台。连接名称与实际地址分开，失效环境收进管理区。用户更换云实例只更新连接与必要的信任、资源映射，不重新拼工作流参数。

“已配置”“可信任”“刚刚在线”“预检通过”“曾成功出图”分别展示，不统称绿色可用。在线探测不会自动下载模型或启动付费实例。新 SSH 指纹仍需明确确认；地址或实例身份变化会使能力和映射失效。同名模型文件不能当作同一权重。

### 6.2 首版选择策略（建议默认值）

1. 从启用且允许自动选择的已保存环境中筛选当前模型、工作流版本、节点、参数和资源要求。
2. 自动模式排序：用户明确偏好 → 上次成功 → 稳定配置顺序。固定模式只检查固定环境，不静默退回自动。
3. 每次生成重新使用最多 30 秒的连通性证据；沿用能力快照最长 900 秒，但配置、实例身份、模板和映射变化立即失效。只读健康检查最多并发 2 个，单候选连接预算 5 秒，单轮路由预算 15 秒；下层调用必须可取消/受超时约束。
4. 大型资源清单检测另走现有异步 inspection；未完成的候选显示“资源检测中”，不能因在线直接接受。后台只在用户进入环境管理/主动检测或提交时按需检查，不持续扫所有远端。
5. 网络失败暂避 30 / 60 / 120 秒；配置错误或未知指纹等待修正。显式“重新检查”可绕过网络退避。超过本轮预算仍有未检查候选时显示“尚未检查完”，允许继续检查同一意图，不能断言所有环境不可用。
6. 优先顺序以两候选一批处理，允许等到当前批的有界截止点；不会因探测竞速每次跳到不同机器。预检成功只是可提交，不承诺 GPU 出图成功。

意图持久化本轮候选顺序、已检查结果、未检查游标与轮次。继续检查先处理 unchecked，避免每轮又被前几台失效机器耗尽预算。候选检查有效期内沿用证据；配置或代次变化只使相关候选失效。只有当前更高偏好候选已明确失败、不可执行或达到它的有界检查期限，才采用后面的合格候选；用户显式重检可以开始新一轮，但不创建新生成意图。

SSH 环境可读取非秘密的机器/系统启动身份并结合配置指纹；无法取得稳定实例身份时显式标记弱证据。同地址、同 SSH key、身份不可读或复用时，不能可靠发现所有重建；提供“此环境已重建”操作递增 environment_epoch。弱身份候选接受前强制刷新所需资源能力，连接恢复、重建或能力漂移也触发重检。对无法证明相同的资产阻止自动选用，并要求校验标识或显式确认当前映射；不凭同地址、同名文件宣称资源相同。

### 6.3 幂等与任务边界

新增逻辑意图接口，保留旧生成端点与既有提交回执协议。前端提供稳定 `clientRequestId`；同键同内容返回同一意图，异内容返回 409。逻辑摘要包含不可变创作输入、所选工作流版本、资源要求和执行策略；不包含探测后才确定的环境。

拟定：`POST /api/v3/generation-intents`、`GET /api/v3/generation-intents/{id}`、`POST /api/v3/generation-intents/{id}/retry-resolution`。状态为 `resolving | blocked | accepted | canceled`。blocked 带具体原因及已检查/待检查候选；修改创作输入需要新意图，单纯继续检查保留同一意图。

后端先查 durable intent，再探测。以租约和 fencing epoch 防止同一意图被并发解析；探测时不持有数据库长事务。接受事务必须同时验证意图租约、工作区 revision、输入与资源指纹，并原子写入冻结 target、既有 submission 和 intent→run 映射。不能靠前端禁用按钮来保证不重复。

仅接受前可切换候选。接受后环境永久冻结，后续任务恢复继续沿用原回执；响应丢失时先查 intent / submission，不换键、不换机重发。服务重启后，若已有 submission 必须先恢复映射，不能再次路由。任务状态未知时只核对原任务，不把网络错误当成“肯定没生成”。

## 7. 数据与入口迁移

- 旧提示词、版本、草稿、图片与 run ID 原样保留；不做破坏性批量改写。
- 新创作默认 auto。旧未提交草稿中显式保存的环境迁为 pinned，保留原意；界面提供一次可撤销的“以后自动选择，优先这台”。旧格式通常只有 remote_profile_id，没有手选/默认来源：证据缺失时一律保守迁为 pinned。只有能证明来自全局默认且没有用户覆盖的情况，才转为 auto 首选；独立全局 last_remote_profile_id 本身可作为新创作偏好。
- 原参数值保留。无法证明配方来源时保守迁为手动覆盖，不根据今天的模板反推昨天的默认值。
- `/direct` 转入统一工作台原文编辑入口，保留旧草稿和项目名称；导入先持久化并记录消费回执，成功后才清除旧交接数据。回译只显示对照，不改正文；无 LLM 配置仍可直接生图。
- `/workbench/conversation` 保留兼容跳转。studio/editorial 偏好映射至 unified，主题值不变。
- pending 请求记录与普通草稿分开迁移。先恢复旧提交，再显示新界面；不能因为启用 auto 生成新请求。
- 新数据表与字段采用增量迁移，保存 schemaVersion。回退 UI 不删除新日志、旧版本或已接受任务；数据库升级前保留用户数据备份。

## 8. 能力去向与清理条件

| 当前能力 | 最终位置 / 处置 |
| --- | --- |
| 会话选择、命名、归档、草稿恢复 | 顶部会话入口；恢复工具在版本面板次级入口 |

| 场景设计、画师推荐、图片对照 | 编辑区工具 / 结果对照，不随布局合并删除 |

| 生成历史与恢复 | 结果 / 任务页；实际来源可回到版本 |

过渡期使用内部开关验证新界面，不能再向用户增加第三种可长期切换布局。只有功能去向表、旧链接、旧数据和验收场景通过后，才能删除旧路由组件与布局 CSS。

## 10. 本轮定下的实施原则

先修已确认断链，再建立版本/参数契约，再加自动路由，最后接入唯一工作台并做迁移清理。现有 `ConversationStudioView` 的展示边界可沿用；大页面中的历史、参数、提交逻辑逐步抽成控制模块，不一次拆空整个应用。新接口优先兼容既有提交与恢复机制，新增依赖仅在确有必要时引入。

本文替代旧设计中与“两套布局”“按服务器×工作流选择执行目标”冲突的建议；未覆盖的业务约定继续沿用。旧文档中的“当前实现”描述属于当时记录，当前事实以本轮代码审查为准。
