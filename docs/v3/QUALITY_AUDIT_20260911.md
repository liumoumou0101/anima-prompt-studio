# 2026-09-11 第一轮质量审计与修复

本轮完成可复现条件修复、作者来源核验、13 张小规模成图与一次完整 API 提交验证。不能把“执行成功”或“同参结果一致”当成全模型质量已经合格；用户昨日普遍观察到的 Aesthetic/Turbo 差距仍需更多场景验证。

## 已修改

- 会话、经典工作台、英文直出和画师对照输入支持精确十进制大 seed。大整数在浏览器传输和展示中用字符串，Python 采样仍用整数，范围为 -1～2^63-1。旧工作台读取和画廊参数展示也做转换，原始工作流文件保持整数。已丢精度的旧浏览器草稿不能凭空恢复。
- 提交哈希仍将 seed 规范化为历史整数形式，避免精度修复破坏旧幂等回执身份。
- 会话增加可见的模型负向建议入口。点击后补到可编辑负向框，不在提交时隐式追加；Base、Aesthetic、Turbo、MiaoMiao 1.6 和 AnimaYume 1.0 Final 分别说明。Aesthetic 建议是依据作者禁止 score_* 的说明裁剪通用列表，尚非独立验收的最优配方。AnimaYume 作者未给出本次能确认的固定负向列表，保留手工输入。
- 修订会话 LLM 合同：应保留用户已经检查、补入的质量负向内容，不再以“没有全局排除”为由要求清空。该规则仍依赖 LLM 遵循，不能宣称任意 LLM 都不会漏词。
- 执行目标标注实验工作流，并展示现有工作流说明。
- 记录任务准备的 SSH、环境检查、编译、节点信息/节点检查、输入检查、提交耗时；失败的阶段也记录。提交服务另记任务准备、目标解析和持久化前耗时。这些不是完整浏览器点击到 GPU 开始执行的追踪，也尚未提供准备阶段硬性总超时。
- 工作流报告复用一个数据库连接，避免对每个映射和开关重复开库、运行迁移检查。保留原有映射失效、指纹、缓存过期和资源校验行为。

## 延迟与完整链路

- 同一台本机、同一数据库、37 条工作流报告，各测三次：修改前中位数 0.422 秒，修改后 0.125 秒，输出完全一致。只证明这个环节约减少 70% 耗时，不是全流程提速 70%。
- 本轮软件协调器执行开始至提交回执约 1.59～2.77 秒；图编译在计时精度内接近零，节点信息/检查约一秒。首次切换模型的总耗时与后续热运行差别很大，不能把首图/热图总时长直接当工作流速度排名。部分前期哈希读取与首组生图重叠，因此首组总时长尤其不适合性能排名。
- 完整 API 使用新建隔离数据库和既有安全凭据，未写用户运行数据库。未预热的能力检查包含在请求内：HTTP 202 回执约 2.55 秒，其中目标解析约 2.53 秒；入队后的准备约 1.91 秒；整张图含切换模型及下载约 58.64 秒。
- API 实收字符串大 seed，实际冻结工作流仍为准确整数；负向文本完整保留。相同 Idempotency-Key 重发返回完全相同回执，没有第二张图。
- 昨天“准备阶段比生图更长”本轮没有复现，仍列为未解决；需要在发生时读取新计时记录，不能以本轮较快就关闭问题。
