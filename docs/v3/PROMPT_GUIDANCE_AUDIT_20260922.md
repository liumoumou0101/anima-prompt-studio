用户问题：既然补充人物朝向、面部可见、月光照到人物、眼睛和衣料细节之后效果明显改善，提示词工具原来的约束和参考里是否已经写过这些要求？

本轮检查当前源码、开发文档、参考目录与历史任务数据库。只新增本报告；不修改生产逻辑，不连接已关闭的云实例，不调用 LLM 或 GPU。以下源码结论针对当前工作树，不宣称已核对所有历史发行包中的相同实现。

## 结论

写过相关内容，但主要是“保留用户指定的光影、构图、视线，避免擅自改变画面”的约束；没有形成针对当前场景检查信息是否足够、再提出适量改进建议的完整指导。

另外，本次原始失败任务明确来自“英文提示词直出”。它没有经过 LLM 改写，所以不能用该批图证明已有 LLM 规则被执行后仍然失效。此前把结果主要归结于模型、夜景能力或用户提示词简单，都缺少对这个入口差异的交代。

这也没有消除产品层面的缺口：即使换到对话工作台，目前生效规则也没有明确要求检查夜景主体的可见性、光线对人物的作用、重要细节的表达，并把缺失项转成有取舍的可选建议。

## 2. 哪些规则已经写了，哪些没有

| 内容 | 当前实现 | 对本案例的意义 |
| --- | --- | --- |
| 保留主体、数量、动作、属性归属、排除项 | `api/conversation.py:143` 起 | 防止改写丢失或误改原意，属于已有要求。 |
| 保留用户选择的景别、布局、机位、视线、氛围 | `core/scene_design.py:49` 起 | 能表达用户明确选择，未指定项保持未指定。 |
| 视线属于哪个人物，机位不等于头部姿态 | `core/scene_design.py:58` 起 | 已有语义区分，不应说“完全没考虑朝向”。 |
| 适量补充环境、纹理、表情 | `api/conversation.py:158` 起 | 扩写模式允许，但规定列出增加内容；没有具体的画面质量检查方法。 |
| 夜景中的脸部是否应可辨、照到哪里、如何保留夜色 | 生效系统规则中未发现明确检查要求 | 用户改进提示中的关键关系没有被系统化为建议方法。 |
| 针对所选生图模型组织描述 | 当前对话请求未显式传入所选生图模型的提示指导 | 不能假设配置了 Aesthetic 工作流，改写 LLM 就自动知道对应写法。 |
| 用自然语言清楚表达光线与主体的关系 | 设计文档有混合表达方向；对话主规则仍写 `tags or short phrases` | 表达载体方面存在不一致，需要实际对比验证，不能断言这句话单独导致了差图。 |

主规则见 [conversation.py](../../v3/src/anima_prompt_studio_v3/api/conversation.py#L114)。第 252–259 行实际构造的输入是系统合同、场景控制规则、忠实/扩写模式，以及当前 requirements、已编译提示词和用户修改。

忠实模式明确只翻译和组织已有事实；扩写模式也明确不能因为“扩写”就改变景别、机位、构图或风格。这些保护有历史原因，不能为了这张图把它们整体删除。

场景设计建议见 [scene_design.py](../../v3/src/anima_prompt_studio_v3/api/scene_design.py#L50)：最多提供三组选择，支持景别、布局、机位、视线、氛围，采用后才成为要求。目前没有独立的主体受光、面部可见性或材质细节建议字段。自由文字仍能表达它们，但系统没有明确指导必须如何思考这些因素。

## 3. “有参考资料”不等于“每次改写都读参考资料”

项目确实保存了资料：

- [Anima 参考图鉴](../../anima-ref/gallery.md)：有不同模型的写法说明，以及带提示词、参数和来源的案例。
- [提示词核心边界](PROMPT_CORE_LESSONS_AND_BOUNDARIES.md)：明确标签负责稳定概念，自然语言负责关系、空间和复杂动作；也要求区别事实与建议。
- `prompt_assistant/config/system_prompts_template.json`：旧通用扩写模板中有光影、构图、人物细节等指导。

但当前对话主链使用 `ConversationService → LLMService.complete`，由调用方直接构造消息。`prompt_assistant/services/llm.py:27` 及 `services/completion.py:66` 的后续处理没有自动把上述图鉴、旧扩写模板或整套案例加入系统消息。

参考钉选的实际作用是把选定案例的结构化要求按层写进当前 requirements，见 [apply_pin](../../v3/src/anima_prompt_studio_v3/core/requirements.py#L408)。它不是每次自动搜索全库、提取优秀案例的写法，再作为示例教给改写模型。选用风格参考时，光影和构图还取决于对应的包含标志。

因此这里至少要区分：开发者能读到的资料、旧模块模板、用户主动采用的参考层，以及本次真正发送给 LLM 的上下文。

## 5. 后续改进方向（本轮未实施）

1. **保留直出和忠实模式的用途。** 不自动把所有人物改成正面、看镜头或亮脸；用户可能正要剪影、背影或暗部。需要增强时提供明确入口。
2. **把画面完整性检查写成推理指导。** 结合用户目标，检查主体姿态和朝向是否足够、关键部位应否可见、光源如何作用于主体、主体与背景如何区分、哪些材质值得描述。只提出与场景有关的少量建议。
3. **区别保真与创作建议。** 用户已有要求必须保留；缺失的创作选择给出可选方向。对“夜景人物肖像”可以建议保留夜色并让面部适度受光，对“月下剪影”则不应补脸部照明。
4. **允许标签与连贯关系句混用。** 用标签固定人数、发色、服装；用关系句表达“柔和月光照亮她的脸与校服，同时保留深蓝夜空”。不设机械字数或句数门槛，也不以堆质量词代替具体描述。
5. **明确接入模型指导和相关参考。** 让所选模型的提示指导进入实际请求；若引入案例，按相关性、模型与 LoRA 依赖筛选，并把参考当数据，不能复制无关角色或风格。
6. **分开验证软件路径和画面收益。** 先验证改写请求确实携带相关指导、尊重锁定与用户选择；以后只有在用户重新提供可用实例并要求继续测试时，再用少量固定 seed 对比原文、当前扩写、改进扩写。

不建议立即写死 `night → facing viewer + face clearly visible + moonlight`。那会把本次有效的一种画面选择错误推广到所有夜景，重新引入项目文档已经指出的默认构图和自动补全问题。
